# School Dashboard

1. In Cloudflare D1, open `family-assignments`, choose **Console**, and run the contents of `schema.sql`.
2. Replace your GitHub repository contents with this folder's contents and push to `main`.
3. Cloudflare Pages redeploys automatically. The existing `DB` binding and three password secrets are used by the new app.

The first successful sign-in imports the assignment lists into D1.

The kids’ dashboard shows Now / Next, Due Today, tomorrow’s unfinished assignments in Working Ahead, and Past Due. Completed work can be reopened. Completing an assignment records its completion date, and the child can record a separate submission date. Parents can also mark assignments complete or reopen them from the shared dashboard. Parents can add or correct both dates and keep a receipt link and note with each assignment. Parents can also attach a direct assignment link, manage help requests, import assignments and schedules, and use per-child schedule headers, reward delivery tracking, and a recent activity feed. The shared dashboard stays read-only for monitor access.

The Family Calendar link is available from the sign-in page, parent workspace, shared dashboard, and both kids’ dashboards. Everyone can view the shared month calendar and daily agenda. Parents can add, edit, and remove all-day or timed events, with an optional location and notes. Calendar events sync through the existing `settings` table and need no database migration.

Settings include light/dark/device appearance, theme previews and high-contrast themes, text size, spacing, and an optional class browser. Signed-in profiles sync settings through D1; shared-dashboard and signed-out settings are saved on the current device. Existing theme choices carry over.

Assignment links, completion and submission dates, receipt links and notes, help flags, and preferences use the existing `settings` table. Existing databases need no migration. Keep the current Cloudflare Pages `DB` binding and password secrets. Upload the HTML, CSS, JavaScript, and `functions` files together when deploying.

Schedules use Eastern Time and are saved per student and date. Editing a schedule does not save it until “Save this day” is selected; imports save the dates found in the pasted calendar. Assignment subjects are specific to each child: every class in that child’s saved schedule gets an assignment slot automatically, including Spanish, Ed Tech, Physical Education, Art, Technology, STEM, and custom-named classes. End times are optional and retained when importing schedules. Older schedules without an end time for the last class show “Latest start” rather than claiming that class is still in session.

Unsaved changes stay queued on the device and retry when connectivity returns. A failed save stays visible with a Retry control; switching accounts waits for pending changes to save.

Run API and date/import checks with `npm test` (Node 22.13+ with built-in SQLite). For a local sample-data preview, run `node tests/test-server.js` and open `http://127.0.0.1:4173`. All three sample profiles use `test-password`; this preview uses an in-memory database, not the live school data. Browser checks run with `node tests/browser.cjs` when Playwright and Chrome are available.

The Rewards Store is available in the signed-in header for parents and children. Assignments completed on the due date earn 1 point; assignments completed exactly one calendar day early earn 2 points. Late completions, completions more than one day early, and assignments without due dates earn 0. Marking an assignment complete on the child’s dashboard records its completion date and calculates points automatically; a separate submission date is optional. Parents can correct dates, add and edit reward names and point prices, and remove rewards. Children can redeem affordable rewards, and parents can see both children’s balances and redemption history. Purchases save their original name and price. Earnings recalculate when assignments are corrected, reopened, or removed, and balances stop at zero. Parents can correct completion dates. Store data uses the existing settings table, with no migration required.

Children start with two free theme palettes: Coastal (light) and Midnight (dark). All other palettes cost 5 points each for a permanent unlock per child. Locked palettes and their preset looks show the price in Settings; purchasing uses the same point balance as rewards and appears in redemption history. Previously selected paid palettes fall back to the free light/dark choices until unlocked. Parent and shared-dashboard themes remain unrestricted. Include functions/api/theme-catalog.js when deploying.

All additional child appearance options use permanent point unlocks: fonts cost 3 points each (shared between text and clock), UI styles cost 5, corners/edges/textures/background effects/avatars/frames cost 2 each, and avatar or background uploads cost 4 per upload feature, allowing unlimited future image changes. The default option in each category is free. Locked options display their price and ask before spending. Preset looks require ownership of both their palette and UI style. Existing unpaid customizations fall back to defaults; parent and shared-dashboard appearance remains unrestricted. Text size, spacing, reduced motion, time format, and dashboard usability preferences remain free. Existing parental font availability controls still apply. Deploy functions/api/cosmetics.js with the other app files; no database migration is needed.
Late completions do not earn assignment points. There are no automatic late penalties or other automatic deductions. Only parents can record deductions through the Parent panel; balances cannot go below zero.

The child dashboard highlights the next open assignment. Marking it complete records the completion date and awards any points due; recording the submission date is optional. Children can pin a store reward as a savings goal, see its progress beneath their name, and clear or change it in the store. The store includes a breakdown of assignment earnings, parent bonuses, deductions, and spending. Parents mark real-world reward purchases delivered from Ready to give; purchases retain their original names and prices. The parent activity feed includes new completions, submissions, help requests, purchases, bonuses, deliveries, and deductions, with a child filter. Appearance items offer isolated previews, Unlock and use, and Using labels. New state is stored in settings; no schema migration is required.

Balances never go below zero. There are no automatic late penalties or other automatic deductions. Only parents can record deductions through the Parent panel; existing historical deductions remain in the ledger. Existing negative balances are reconciled to zero with a visible balance correction on the next sign-in, refresh, or save. Server-side purchase checks use the same spendable balance and atomically block unaffordable reward, theme, and cosmetic purchases. Completed assignments retain their earned points when merely reopened, preventing a spent completion from creating debt or awarding its points twice.

The dashboard point rules explain school and behavior points. Only work completed on its due date (1 point) or exactly the day before (2 points) earns assignment points; completions two or more days early earn 0, enforced in server-side balance and purchase calculations. Children earn points by marking work complete; a separate submission date is optional. Parents can correct completion and submission dates. Parent dashboard child headers include Deduct points. Presets charge 2 points for more than two submitted quiz attempts; 1 for schoolwork refusal/whining, not listening, or skipped assigned chores; fighting charges 1 to each child in one transaction. Parents can record other deductions with an amount and required explanation, and award bonuses for good behavior/helpfulness outside schoolwork. Quiz attempts and behavior are parent-recorded, not automatically imported. Deductions are retry-safe, stop at zero, and appear in history, breakdowns, and the parent activity feed. Deploy functions/api/point-rules.js with the app.

Children can see and complete only assignments due by tomorrow (plus undated work); Working Ahead shows only tomorrow and never skips to a later date after completion. The server rejects student completion/submission changes for work due beyond tomorrow, while parents retain editing access. Submitted events in the parent Recent Activity feed include Undo submission, which reopens the specific assignment and clears completion/submission dates, recalculates points, and records a reopened event. Older events use a unique title match only when unambiguous.

Page Pals are available in the Rewards Store. Each child can buy a pal at its curated base price (5, 7, 9, or 12 points), upgrade for base + 5, then base + 10 points, and equip one roaming companion or put it away. Static pixel sprites bob, hop, and flip direction; reduced motion is respected. The generated catalog in functions/api/page-pals.js uses assets/Page Pals filenames in numeric form order, with form 2 acting as the initial form when form 1 is absent. Purchases and equipped pals sync through settings without a migration. Deploy page-pals-ui.js and the sprite folder alongside the app. Font assets now live under assets/fonts, including the optional-fonts stylesheet and its assets.

Parent and shared dashboards have a Page Pals header button with free access to every pal and form. Their equipped test pal is saved separately per dashboard on the current device and does not spend child points or change child collections.

Page Pal base prices are curated in functions/api/page-pal-prices.js following visual review of the starting and final sprites: 314 pals at 5 points, 187 at 7, 66 at 9, and 41 at 12. The store and server share this price catalog; existing purchases keep their paid price and ownership. Include this module when deploying.



Every Page Pal form uses the exact fighter name from the sprite pack README.txt, copied into docs/page-pal-source-list.txt. The table directly maps all 608 family IDs and 1,822 existing sprite forms; filenames and physical suffixes are preserved, including 001-2 Jollyjack / 001-3 Hinkypunk and 002-2 Mo'lagos / 002-3 Leep-a-Lil. The two absent form-1 placeholders are never offered as sprites. functions/api/page-pal-names.js replaces all invented and inferred names; docs/page-pal-name-matches.json records the exact ID/form mapping. Previous purchases retain their recorded titles and ownership. Deploy page-pal-names.js with the catalog. Catalog browsing preserves page, filter, scroll and form focus.

The Rewards Store now opens immediately to three departments: Rewards, Page Pals, and Appearance. Point rules are a compact dashboard disclosure; balance details and purchase history no longer crowd the shop. Parent and shared dashboards use the same store entrance. Store refreshes use functions/api/rewards-store.js instead of reloading the complete dashboard. Dashboard and purchase responses contain pal metadata only for the equipped family; only the requested page of 24 named pals is fetched on demand from /api/page-pals-catalog. All 1,822 names exactly match the sprite pack list. Deploy rewards-store-ui.js, both new API handlers together with the app.

Page Pal browsing requests one page at a time (24 families), with visited pages cached in memory and persistently on the device. My pals requests only the IDs on the visible page. Sign-in, dashboard refreshes, and the Rewards Store landing do not fetch catalog pages. Parent/shared equipped preview metadata is saved locally alongside the selection so reloading does not fetch a catalog just to display that pal. Names and prices are served directly from the source catalog, with no generated full-catalog asset.

A tiny catalog-version check runs only when Page Pals is opened. Visited pages are reused across reloads; a changed name, price, form, or crop produces a new version so stale pages are refreshed. Versioned page responses and static assets have long-lived browser cache headers. Clicking an equipped pal stops it at its current position for 1.5 seconds, then resumes wandering; repeated clicks reset that pause. Visible alpha bounds for every sprite are in functions/api/page-pal-bounds.js, so the art fits the same 88px frame regardless of transparent canvas padding. Catalog cards and previews use the same crop metadata. Deploy _headers and both Page Pal data modules with the app.

Opening Rewards Store is now entirely local: it uses the last loaded dashboard balance without saving, fetching, or rebuilding after a background response. Refresh balance is an explicit store action; purchases still validate the current balance on the server. Store backdrops avoid full-screen blur. HTML and app scripts revalidate, with content revisions in index.html so updates replace older cached code; pal images and versioned pages retain their long-lived caches.

Assignment imports mark items labeled Completed or Submitted as complete without requiring a numeric score. Negative statuses such as Not submitted remain open. Imported status does not invent a completion date or award points.
